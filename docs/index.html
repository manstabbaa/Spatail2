With Spatail

Built by you.

Put the headset on, walk anywhere, and say what you need. Spatail looks at what the device senses at that moment, has Claude write a small program for that request in that place, and runs it around you.

What AI did to software, Spatail does to mixed reality.

Loading the lab...

This is the Space Lab, a stand-in for the headset. It runs the same program text and the same runtime library as the Quest and iOS apps, drawn with Three.js instead of Unity. On this page the programs are recorded ones written by hand. Choosing Planner (Claude) needs the planner service running on your machine; open the lab from it at http://localhost:8787/lab/ and Claude writes each program from the frame the lab camera sees.

The idea

Software written for one request in one place

A model that can write code after looking at a space can build whatever the moment calls for. So Spatail is a runtime, and it leaves out the two things mixed reality apps are normally built on.

a menu of content types

No taxonomy

There is no list of "walkthrough", "chart" or "checklist" for the model to choose from. It writes a program against a small spatial API and can draw anything it can describe: a marker on one bolt, a distance between two things, a route on the floor, a procedure wrapped around a machine, or something nobody has asked for before.

a room scanned and labelled in advance

No prepared environment

Nothing about the place is loaded, registered or remembered. Each request carries the camera frame from that moment, a grid of depth samples and whatever flat surfaces have been noticed so far, which is often very few. The program keeps reading the space while it runs.

The six requests from the film are six ordinary programs

Nothing in the runtime knows what a walkthrough or a dashboard is. Each row is a program the planner could have written; these six were written by hand so the film can be replayed with no network. They use a stand-in pump placed in the Workshop space.

Unprepared places

Testing where nobody has been

The product is someone walking through a factory, a room or a street with the app knowing nothing ahead of time. Three ways to test that, from cheapest to most real.

At your desk

Generated spaces

The lab builds plant rooms, offices and streets from a seed. Nothing in them is labelled and no surface is known at the start: surfaces are found as you look at them, the way plane detection finds them on a device.

Pick one, look around, and watch the surface count grow.

Every place you have been

Episodes

Any request can be saved with its frame, depth samples and words: from the lab, or from the dev tool on site. Replay runs all of them through the planner again and checks that every returned program starts.

Run it after changing the instructions, the API or the model, to see the effect across everywhere you have walked. Frames stay in a git-ignored folder.

On site

The dev tool

On the phone, the Space tab shows what the sensor has found and the frame that was sent. Experiences shows what came back and its log. Code lets you fix the program where you stand and run it again.

The headset app logs the same line whenever sensing changes, for example Depth sensing on, 3 surfaces so far. Camera on.

What to look for in an unprepared place

  • Ask before looking around. The surface list is nearly empty; the program must still work from the frame and the depth grid.
  • Ask about something small and off centre. Does the marker land on it, or on the wall behind it?
  • Ask, walk three metres, ask a follow-up. Content from the first request stays where it was seen.
  • Ask for something with no obvious form ("where would a spill go?"). This is where a fixed menu would have failed.
  • Ask somewhere with no floor in view, or outdoors with nothing within range. The program should say so plainly.

The two apps

One runtime, a headset app and a dev tool

Both apps are thin shells around the shared package com.spatail.core. Each supplies a camera, a sensor that answers ray casts and captures frames, a pointer, and text or speech input. Press Play in either Unity project without a device and the same runtime starts in a simulated room.

Planner service

Where Claude sees the frame and writes the program

Devices never hold a model API key. They send the request, the frame and the sensed context to this small service; it calls Claude and returns a program, a one-line reply and a title for the "Built ..." chip.

Run it

Then open http://localhost:8787/lab/ for the lab with Claude writing the programs, or set the planner address to this machine's LAN address in the iOS dev tool's Settings and push it to a headset from the Link tab.

What one call looks like

  • The instructions with the API reference, and your organisation's knowledge, go in two cached system blocks. Repeat requests read most of their input from the prompt cache.
  • The camera frame goes in as an image, followed by the depth grid, surfaces so far, what is already running and what was said.
  • The answer is constrained to a small schema: reply, title, id, code, remove, clear.
  • If the program fails to start on the device, the device sends it back once with the error for repair.
  • If the model declines, the API retries on its fallback model within the same call. Failures come back with error set and the device says so.
